7. Three Sequential DB Queries on NoteLive Mount

Mount calls:

8. DB Query Inside build_subscription_filter
File: lib/mist_web/live/note_live/index.ex lines 310–318

When the filter is {:list, list_id}, the function calls Profile.get_pubkeys_in_list(list_id) inline during subscription building. This is a DB hit happening inside the LiveView process's synchronous event handler path. The same call is also made in reload_notes_for_filter, so for list filters, two DB queries for pubkeys fire on every filter change. The pubkeys should be stashed in socket assigns when the list is selected, like follow_pubkeys is for the :following filter.

9. refresh_relay_assigns Fires N Background Tasks on Every Action
File: lib/mist_web/live/relay_live/index.ex lines 136–147

Every connect, disconnect, delete, and form save calls refresh_relay_assigns, which loops over every relay and sends a {:fetch_relay_info, ...} message for any stale/missing metadata. Each message spawns a supervised HTTP task. If a user has 10 relays and clicks connect/disconnect in quick succession, this stacks up batches of tasks hitting the same relay endpoints. There's no deduplication or in-flight guard.

10. Duplicated upsert_metadata / get_or_create_metadata
File: lib/mist/relay.ex lines 124–137, 198–212

Both get_or_create_metadata/2 (public) and upsert_metadata/2 (private) implement the same read-then-insert-or-update logic for Metadata. Only upsert_metadata is actually used internally. The public one is dead code and creates confusion about which to call from outside.
